# 歌词在线匹配与本地标签兼容设计

## 状态

已确认设计，等待实现计划。

## 背景

Coriander Player 已支持本地 LRC、KRC、QRC 和 TTML 歌词，也已经有在线歌词来源选择窗口和本地歌词索引。当前 Rust 标签读取路径通过 Lofty 的 `ItemKey::Lyrics` 读取统一的歌词字段；用户实际用 Mp3tag 写入的 `LYRIC`（单数）字段没有被该路径识别。用户提供的 `LYRIC` 内容是带时间戳的 LRC 文本，本身可以由现有 Dart 解析器解析。

在线匹配目前集中在 `lib/music_matcher.dart`：只使用音频标题查询，QQ、酷狗和网易云按顺序调用；任一返回格式或网络异常都会结束整个搜索；候选评分是按标题、艺术家和专辑的字符位置进行的简单比例；歌词正文只尝试排序后的第一条候选。现有“默认歌词”窗口已经可以展示候选并允许用户手动选择，但候选获取和失败回退不够可靠。

## 目标

1. 本地读取同时兼容 `LYRICS`、`LYRIC` 以及现有支持的嵌入式和同名 `.lrc` 歌词。
2. Mp3tag 修改音频后，本地歌词索引能够根据实际文件修改时间发现变化，不要求用户重建整个媒体库。
3. 在线搜索结合标题、艺术家、专辑、时长和版本信息，提高首选候选的准确率。
4. QQ、酷狗、网易云相互隔离；单个来源失败不影响其他来源返回结果。
5. 多候选时自动使用最高可信度候选；最高候选正文获取失败时继续尝试后续候选。
6. 保留候选列表供用户查看、预览和手动切换；手动选择继续沿用现有来源持久化机制。
7. 成功获取的在线歌词可缓存，断网时可复用最近结果，但不自动写回音频标签。

## 非目标

本期不包含以下内容：

- 更换为第三方聚合歌词服务或新增需要账号的服务。
- 自研歌词解码器或修改已有 LRC、KRC、QRC、TTML 的时间轴语义。
- 自动把在线歌词写入 MP3、FLAC、MP4 等音频文件。
- 自动删除或覆盖用户已有的 `LYRIC`、`LYRICS` 或其他标签。
- 修改当前的本地/在线优先级、逐曲指定歌词来源入口或独占播放模式。
- 为了扩大覆盖面而盲目升级 `music_api`；先隔离当前固定版本的 API，只有验证兼容后才考虑单独升级。

## 用户体验

### 本地歌词

读取嵌入式歌词时按以下顺序寻找可解析文本：

1. 标准 `Lyrics` 映射对应的值。
2. 原始标签项中键名大小写不敏感的 `LYRICS`。
3. 原始标签项中键名大小写不敏感的 `LYRIC`。
4. 同目录同名 `.lrc` 文件。

每个候选值都经过现有 TTML/LRC 解析器验证；只有包含有效时间戳并产生歌词行的值才被采用。多个标签值同时存在时优先使用顺序靠前且可解析的值，不改变任何文件内容。纯文本、没有时间戳的值仍按当前规则视为不可用于同步歌词。

用户在 Mp3tag 中保存 `LYRIC` 后，播放器重新扫描该文件或触发歌词索引同步即可发现新内容；不要求手动把字段改名为 `LYRICS`。

### 在线自动匹配

播放歌曲时继续遵守现有本地优先/在线优先设置。需要在线歌词时：

1. 生成清理后的主查询（标题 + 艺术家），标题查询作为无艺术家信息时的回退；专辑信息仅在需要扩大结果时补充。
2. 对每个来源独立搜索，并取得多条候选，而不是只保留第一条。
3. 对候选去重、评分并排序。
4. 最高分且达到可信阈值的候选自动成为当前歌词。
5. 当前候选正文为空、格式无效或请求失败时，自动按排序继续尝试下一条。

自动匹配只影响当前播放，不自动写入逐曲来源配置；用户在候选窗口明确点击某一条后，才沿用现有 `lyric_source.json` 记录该选择。

### 候选切换

现有“默认歌词”窗口继续作为候选入口，并增强为：

- 显示来源、歌曲标题、艺术家、专辑和歌词类型。
- 显示匹配分数或简短匹配原因，帮助用户判断版本差异。
- 对正文获取失败的候选跳过或标记失败，不阻塞其他候选。
- 点击候选立即预览并切换当前歌词；手动选择继续持久化源 ID/哈希。

候选列表至少保留各来源的前若干条高质量结果，并保留跨来源去重前的来源标识，避免同一首歌只有一个来源可选。

### 在线缓存

成功解析的在线歌词和必要的候选元数据保存在应用数据目录，不写入音乐目录。缓存键包含音频路径及标题、艺术家、专辑等元数据指纹；音频元数据或文件修改时间变化后视为旧缓存。缓存读取失败、损坏或过期时回到在线搜索，不影响播放。缓存只保存有限数量的最近结果，并提供随应用数据清理而失效的自然边界。

## 架构和数据流

### 本地标签读取

在 `rust/src/api/tag_reader.rs` 的 Lofty 读取函数中保留 `ItemKey::Lyrics` 快速路径，并增加原始标签项遍历的别名查找。别名比较使用 Unicode 大小写折叠后的键名，只接受 `LYRIC` 和 `LYRICS`；值提取后按优先顺序交给 Dart 侧 `parseLocalLyricText`。Rust 侧继续在嵌入式读取失败后尝试同名 `.lrc`，不改变现有编码处理。

`lib/lyric/lrc.dart` 继续负责 TTML/LRC 解析和 `┃` 翻译拆分，不为 `LYRIC` 增加另一套解析逻辑。这样 `LYRIC` 和 `LYRICS` 在上层得到完全相同的歌词对象。

`lib/library/lyric_search_index.dart` 的歌词指纹改为读取音频文件的实际 `lastModified`；保留现有同名 `.lrc` 路径和修改时间字段。已有索引格式保持 v2，只有指纹变化的歌曲重新读取，不触发全库无条件重建。

### 在线来源适配层

在 `lib/music_matcher.dart` 内部建立统一的来源适配契约，每个适配器提供：

- 以查询文本返回原始搜索项并转换为统一 `SongSearchResult`。
- 根据来源 ID、哈希或歌曲 ID获取歌词正文。
- 来源名称、候选标识和错误上下文。

QQ、酷狗和网易云适配器各自负责字段缺失、返回结构变化和异常记录。`uniSearch` 使用独立的 future 和超时保护汇总结果；一个适配器失败时记录错误并返回空列表，其他适配器仍继续执行。搜索候选数量设为可配置的有限上限，避免请求失控。

`getMostMatchedLyric` 改为遍历排序后的候选，尝试获取并解析歌词，返回第一条有效歌词；获取过程不改变候选列表，来源窗口仍可按同一候选对象单独预览。

### 标准化和评分

新增纯函数式音乐元数据标准化层，复用现有歌词搜索标准化中的简繁转换和 Unicode 处理能力，但不改变界面显示文本。标准化至少包括：

- Unicode 大小写、空白和常见标点统一。
- 去除标题前的曲号和无意义空白。
- 将 `feat.`、括号中的版本词、Live、Remix、现场、伴奏等提取为可比较的版本标记，而不是一律删除。
- 标题、艺术家和专辑分别生成可比较形式；中文可比较形式兼容简繁差异，必要时复用完整拼音形式。

评分按字段加权，标题精确一致权重最高；标题包含、艺术家重合、专辑重合和时长接近依次提供加分；版本标记冲突、明显不同的艺术家或时长差异提供惩罚。评分函数必须是确定性的，并返回可供 UI 使用的简短原因。低于可信阈值的结果不自动采用，但仍可在用户主动查看候选时显示。

跨来源去重使用标准化后的标题、艺术家和专辑组合键；去重只影响排序展示，不丢弃来源 ID，以便在来源间切换。

### 自动结果与手动来源

自动播放路径只消费“首个有效歌词”结果，不把自动结果写入 `LYRIC_SOURCES`。候选窗口继续调用统一搜索和歌词获取方法；点击候选后才调用现有 `useSpecificLyric` 并写入对应 `LyricSource`。已有手动来源优先规则不变：指定来源读取失败时显示失败状态，不静默改写用户选择；用户重新执行在线搜索后才重新评估候选。

### 缓存边界

新增独立的在线歌词缓存模块，缓存对象包括：候选来源、来源 ID、匹配元数据、解析成功的歌词文本和写入时间。缓存读写使用临时文件加原子替换，损坏时删除缓存项并回退在线请求。缓存不得进入音乐文件目录、歌词索引或 `lyric_source.json`，避免与本地来源选择和索引迁移互相污染。

## 异常处理和兼容性

- Lofty 无法读取文件、标签值为空或别名值无法解析时，继续尝试下一个标签值和同名 `.lrc`。
- 多个本地标签值都有效时只采用固定优先顺序的第一个，不随机选择。
- 单个在线来源超时、HTTP 错误、字段缺失或歌词格式错误只淘汰该来源候选。
- 所有在线候选均失败时，保持现有“无歌词”状态，不阻塞播放。
- 自动首选歌词正文失败时，必须继续尝试下一候选；不能因为第一条失败返回空结果。
- 缓存损坏、过期或版本不兼容时忽略缓存并重新在线搜索。
- 已有 `lyric_source.json`、歌词索引 v2 和旧设置保持可读；不因为新增缓存或标签别名删除用户配置。
- 网络搜索和缓存均不自动修改音频文件。

## 测试和验收

### Rust/Dart 本地读取测试

- 标准 `Lyrics`、`LYRICS` 和 `LYRIC` 标签分别能读出相同的 LRC 文本。
- 标签键大小写变化仍能识别；无效或纯文本值会继续尝试下一个候选。
- 嵌入式歌词不存在时，同名 UTF-8/UTF-16 `.lrc` 仍可读取。
- Mp3tag 修改音频后，新的文件修改时间导致歌词索引条目刷新。

### 匹配器单元测试

- 标题+艺术家查询优先于标题单独查询，缺少艺术家时仍能搜索。
- 简繁、标点、曲号、`feat.` 和版本标记的标准化结果符合预期。
- 标题精确匹配优先于只有艺术家或专辑相似的结果。
- 时长接近加分，Live/Remix/伴奏等明显版本冲突扣分。
- 跨来源重复结果能去重但保留各来源标识。
- 一个来源抛出异常时，另外两个来源的候选仍被返回。
- 第一候选歌词获取失败时，`getMostMatchedLyric` 返回下一条有效歌词。

### UI/缓存测试

- 候选窗口显示多个来源和匹配信息，并允许点击任意有效候选切换。
- 自动匹配使用最高可信候选；手动点击后来源 ID/哈希仍能持久化并在下次播放优先使用。
- 缓存命中可以离线加载；缓存损坏或过期会回退在线搜索。
- 搜索和缓存过程不会调用音频标签写入接口。

### 验收标准

1. 用户仅在 Mp3tag 中写入 `LYRIC` 后，播放器重新扫描即可显示该 LRC 歌词。
2. 同一首歌存在多个在线候选时，播放页面自动显示最高可信候选，来源窗口仍能切换其他候选。
3. 第一候选正文不可用时，播放器能自动显示下一条有效候选，而不是直接显示无歌词。
4. QQ、酷狗或网易云任一服务不可用时，其他来源仍能返回结果。
5. 标题带曲号、括号版本或 `feat.` 时，匹配不会因为格式差异直接失败。
6. 现有本地/在线优先级、逐曲来源选择、LRC/KRC/QRC/TTML 解析和播放流程不回归。
7. 在线缓存可在断网时提供最近成功歌词，且不在音乐文件中产生新写入。

## 发布和迁移

本期不改变歌词索引格式版本和现有来源配置格式。首次运行包含缓存逻辑的新版本时，缓存目录可以为空；已有歌曲按实际文件修改时间增量刷新。`LYRIC` 兼容属于读取路径增强，不要求用户批量重写已有文件。实现完成后再根据定向测试结果决定版本号和发布方式。
