# Coriander Player TTML 与 LRC 本地歌词支持设计

**日期：** 2026-08-05  
**状态：** 用户已确认方案，待审阅设计文档  
**范围：** Windows 版 Coriander Player 的本地内嵌歌词和同名 `.lrc` 外挂歌词

## 1. 目标

当前播放器可以读取音频标签中的歌词文本，但只按 LRC 方括号时间戳解析。部分 FLAC 文件把歌词保存为 Apple/iTunes TTML：

- `itunes:timing="Line"` 表示逐行歌词；
- `itunes:timing="Word"` 表示逐字歌词；
- 行由 `<p begin="..." end="...">` 表示，逐字时间由嵌套 `<span begin="..." end="...">` 表示。

本次改动要让这两类 TTML 与现有 LRC 都能：

1. 在正在播放页面显示；
2. 根据时间轴滚动并定位当前歌词；
3. 参与现有本地歌词搜索；
4. 保留现有 LRC 和外挂 `.lrc` 行为。

## 2. 非目标

- 本次不加入 QRC、KRC、ID3 SYLT 或纯文本歌词格式；
- 不修改音频文件和 Mp3tag 标签；
- 不新增在线歌词来源、下载或缓存逻辑；
- 不修改 `desktop_lyric` 项目；
- 不重做歌词页面 UI、滚动居中逻辑和逐字高亮组件。

## 3. 现状与根因

Rust 的 `get_lyric_from_path` 已经通过 Lofty 读取 `ItemKey::Lyrics`，能够把 FLAC `LYRICS` comment 的原始文本传给 Dart。当前 Dart 入口 `Lrc.fromAudioPath` 无论文本格式是什么，都调用 `Lrc.fromLrcText`。

`Lrc.fromLrcText` 只识别类似 `[00:12.34]歌词内容` 的行。TTML 文本没有这种时间戳，因此解析后没有有效行，最终被播放器视为没有本地歌词。该问题发生在“原始标签读取”和“歌词界面”之间，不需要改动 Rust 标签读取或 UI。

## 4. 设计方案

### 4.1 统一歌词文本解析入口

新增一个统一解析函数，例如 `parseLocalLyricText(String text)`，返回 `Lrc?` 或空值。入口按以下顺序识别：

1. 去除 UTF-8 BOM 和首尾空白；
2. 使用 XML 解析器判断根元素的本地名称是否为 `tt`；
3. 根元素为 `tt` 时交给 TTML 解析器；
4. 其他文本交给现有 LRC 解析器；
5. 没有有效歌词行时返回空值，不抛出到播放流程。

`Lrc.fromAudioPath` 保留现有调用名称和本地歌词来源语义，但内部改为调用统一入口。Rust 仍只负责返回原始歌词字符串。

### 4.2 TTML 数据映射

新增 `Ttml` 解析实现。`Ttml` 作为本地歌词结果类型保留 `LrcSource.local` 语义，并复用现有 `Lyric`、`SyncLyricLine` 和 `SyncLyricWord` 模型：

- 每个有效 `<p>` 生成一条歌词行；
- `<p>` 的 `begin` 和 `end`（或 `dur`）转换为毫秒；
- 含有有效 `<span>` 的 `<p>` 生成 `SyncLyricLine`，每个 `<span>` 生成一个 `SyncLyricWord`；
- 没有 `<span>` 的逐行 `<p>` 也生成可显示的同步行，用整行文本作为一个词，时间长度使用 `<p>` 的持续时间；
- 读取元素的可见文本，保留歌词中的必要空格；
- 按开始时间排序，忽略缺少时间或没有可见文本的节点；
- 同时支持当前文件使用的十进制秒数（如 `19.311`）和 `hh:mm:ss.mmm` 时钟格式；
- 无法计算 `end` 时优先使用 `dur`，再使用下一子节点开始时间或父行结束时间；无法确定时间的节点跳过。

TTML 解析结果仍标记为本地歌词，因此歌词来源控件、播放定位和现有 `LyricService` 不需要新增在线分支。现有 `LyricViewTile` 已支持 `SyncLyricLine`，可直接保留逐字高亮。

### 4.3 LRC 兼容

现有 `Lrc.fromLrcText` 作为 LRC 分支保持不变，继续支持：

- 普通 `[mm:ss.xx]` 行；
- 同一行多个时间戳；
- `[offset:...]`；
- 同名外挂 `.lrc` 文件；
- 当前项目已有的本地歌词搜索索引。

统一入口只负责选择格式，不改变现有 LRC 的合并、排序和偏移行为。

### 4.4 本地歌词搜索

当前搜索索引只收集 `UnsyncLyricLine`。TTML 逐字歌词会产生 `SyncLyricLine`，因此索引读取逻辑需要改为收集所有带有非空 `content` 的歌词行：

- `UnsyncLyricLine` 使用现有文本；
- `SyncLyricLine` 使用拼接后的整行 `content`；
- 搜索结果仍只展示歌曲信息和命中歌词片段，不播放歌曲；
- 索引格式和增量指纹不变，音频文件修改后重新解析。

这样 TTML 歌词既能播放显示，也能被之前的本地歌词搜索功能找到。

### 4.5 依赖与错误处理

使用 Dart XML 解析库处理 TTML；如果当前 `xml` 仅作为传递依赖，则将其声明为应用的直接依赖。解析器必须：

- 对 XML 语法错误、未知时间格式和缺少时间属性安全返回空结果；
- 不因为单首歌曲格式损坏而中断整次音乐库加载或歌词索引构建；
- 保留现有日志路径，便于区分“没有标签”“格式无法识别”和“格式解析失败”。

## 5. 测试设计

### 5.1 解析器单元测试

- 解析逐行 TTML，验证行文本、开始时间和结束时间；
- 解析逐字 TTML，验证词顺序、词时间和整行文本；
- 验证十进制秒数及 `hh:mm:ss.mmm` 时间格式；
- 验证带 BOM、空白、`dur` 和缺失可选属性的输入；
- 验证 malformed XML、无文本节点和无有效时间时返回空结果；
- 验证普通 LRC、多个时间戳和 `offset` 行保持原有结果。

### 5.2 集成与回归测试

- `Lrc.fromAudioPath` 能根据原始文本自动选择 TTML 或 LRC；
- `LyricService` 能使用 TTML 结果更新当前歌词行；
- 本地歌词索引能收集 TTML 同步行并按整行文本搜索；
- 现有歌词滚动居中、歌词搜索结果和三个已发布功能的测试继续通过。

## 6. 验收标准

1. 播放本次发现的 TTML 逐行歌曲时能显示并随时间定位；
2. 播放 TTML 逐字歌曲时能显示逐字高亮；
3. 播放现有 LRC 歌曲时行为不变；
4. TTML 和 LRC 歌词都能进入本地歌词搜索索引；
5. 单首损坏或不支持的歌词不会导致播放器崩溃或阻塞音乐库；
6. 所有新增测试和现有相关测试通过，针对性分析无新增错误。

## 7. 发布边界

本设计只定义代码和测试改动。实现完成并验证通过后，再单独决定是否合并到 fork `main`、构建新的 Windows Release；本阶段不自动发布安装包。
