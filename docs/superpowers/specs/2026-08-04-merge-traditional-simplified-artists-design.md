# 简繁艺术家全局合并设计

## 背景

当前音乐库使用音频元数据中的艺术家原文作为 `artistCollection` 的 `Map` 键。繁体名称和简体名称字符串不同，因此同一位艺术家会被建立为两个 `Artist` 对象，并在艺术家列表、专辑筛选、歌曲详情和搜索结果中分别出现。

## 目标

- 在全局艺术家数据流中合并繁体和简体艺术家名称。
- 合并后的界面统一显示简体名称。
- 繁体和简体输入都能查找到同一个艺术家。
- 保留原始音频元数据，不修改文件标签。
- 音乐库重新扫描或刷新后，合并结果可自动重建。

## 非目标

- 不修改音频文件中的艺术家标签。
- 不做拼音、大小写、空白、标点或别名语义识别。
- 不尝试判断两个不同的人是否仅因为同名而应合并。
- 不改变现有的艺术家分隔符、专辑排序和“无分类”行为。

## 设计方案

### 规范化服务

新增独立的艺术家名称规范化服务，提供以下职责：

- 将繁体中文转换为简体中文。
- 对英文、数字、标点和无法转换的字符原样返回。
- 只执行繁体到简体转换，不执行拼音、大小写或额外清洗。

转换实现优先采用 `opencc` Dart 包的 T2S 模式，使用完整的 OpenCC 繁简转换规则，而不是手写少量常用字映射，以覆盖生僻字。该包支持 Windows，但使用 native-assets，因此实施时需要验证 Flutter Windows 和 GitHub Actions 构建链。转换器应保持纯函数特性；单个字符无法转换时保留原字符，不阻断音乐库加载。

### 音乐库集合

在 `AudioLibrary._buildCollections()` 中，对每个拆分后的原始艺术家名称先计算规范名称：

```text
原始艺术家名 → 简体规范名 → artistCollection[规范名]
```

示例：

```text
張學友 → 张学友
张学友 → 张学友
```

两个原始名称会加入同一个 `Artist` 对象，且 `Artist.name` 使用简体规范名称。

同时维护原始名称到规范名称的别名映射：

```text
原始名称 → 规范名称
張學友 → 张学友
张学友 → 张学友
```

### 统一回查入口

新增统一的 `artistForName(String rawName)` 查询入口。所有根据歌曲元数据查找艺术家的页面都通过该入口获取对象，不再直接使用原始名称索引 `artistCollection`。

至少覆盖：

- 歌曲详情页。
- 正在播放页的艺术家菜单。
- 专辑详情页的艺术家列表。
- 艺术家列表与艺术家详情页。
- 全局搜索结果。

`Album.artistsMap` 同样使用规范名称作为键，确保专辑详情不会重复展示同一艺术家。

### 搜索和筛选

艺术家搜索查询也先进行繁转简规范化，因此以下两种搜索得到相同结果：

```text
張學友 → 张学友
张学友 → 张学友
```

专辑的“无分类”、排序和按艺术家筛选行为保持现有语义不变，只是艺术家集合中的名称已经合并。

## 数据刷新与兼容性

- 每次 `AudioLibrary.initFromIndex()` 重建集合时重新执行规范化，不需要迁移已有持久化数据。
- 原始音频元数据保持不变，重新扫描后仍能通过别名映射回查。
- 非中文艺术家名称的规范化结果与原文一致。
- 如果规范化后多个不同原文得到同一简体结果，则按本需求视为同一艺术家。

## 测试策略

新增或补充以下测试：

1. 繁体名称转换为简体名称。
2. 简体、英文、数字和标点保持预期结果。
3. 繁体与简体名称进入同一个 `Artist` 对象。
4. 原始繁体名称可通过别名回查合并后的艺术家。
5. `Album.artistsMap` 不产生重复艺术家。
6. 使用繁体或简体查询都能命中艺术家。
7. 音乐库刷新后合并结果保持一致。
8. 现有艺术家筛选、无分类和排序测试继续通过。

验收示例：

```text
歌曲 A：艺术家 = 張學友
歌曲 B：艺术家 = 张学友

艺术家列表：张学友只出现一次
按“张学友”筛选：同时包含歌曲 A 和歌曲 B 所属专辑
搜索“張學友”：命中“张学友”
```

## 风险与回滚

主要风险是繁简转换存在少量语义合并损失，以及新增转换依赖带来的构建体积或平台兼容性影响。规范化逻辑独立封装后，可以通过移除规范化步骤恢复原始精确字符串分组；不需要改动音频文件或持久化索引，回滚范围可控。
